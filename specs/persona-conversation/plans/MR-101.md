## Goal
An owner can create a person ("Margaret Thomas", other names "Mom", "Mum"), link their
own memories to it, and delete it without losing the memories. Every later ticket hangs
off `person.id` and the access helper written here.

## Design
- `Person`: `id`, `owner_id` (FK user, CASCADE), `name` (1–255), `other_names` (JSON list of str, ≤ 10 items, each 1–255, trimmed, duplicates dropped case-insensitively), `created_at`.
- Endpoints, all owner-only:
  - `POST /persons/` → 200 `PersonPublic`
  - `GET /persons/` → caller's persons only, `skip`/`limit` like `/memories/`
  - `GET /persons/{id}`, `PATCH /persons/{id}`, `DELETE /persons/{id}` → `Message`
  - `PUT /memories/{id}/person` body `{person_id}`; `null` unlinks. 403 if the memory or the person isn't the caller's; 404 if either is missing.
- `get_person_or_error(session, user, person_id)`: 404 missing, 403 not owner. **Superusers get no extra access** (unlike memories), following the spec's privacy default.
- `get_person_for_conversation(...)`: same as above for now; MR-107 widens it to members. It is the only place that decides who reaches a persona.
- Linking does not touch `person_name` or trigger re-extraction.

## Risks and how we handle them
- **Two migration heads.** MR-102 and MR-104 also add migrations after this one. Whoever merges second runs `alembic merge heads` (skill step 4); never hand-edit `down_revision`.
- **SET NULL vs cascade.** SQLModel's `Relationship` would cascade-delete memories if declared on `Person`; don't declare `Person.memories` with `cascade_delete`. Covered by `test_delete_person_keeps_memories`.
- **Coverage gate 90%.** Every route branch (404, 403, 422) gets a test.
- **Memory text in errors.** Details stay generic ("Person not found", "Not enough permissions").
