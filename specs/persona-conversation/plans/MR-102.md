(`confirmed_at`, confirm and undo endpoints, confirm all) and the retrieval the persona will
use (`search_persona`, `persona_quotes`), without changing search for anyone else.

## Design
- Routes follow the real router (`/memories/{memory_id}/extracted/{extracted_id}`); the ticket and spec wrote `/extracted-memories/{id}/confirm`, which does not exist (DEV-4).
- Confirm and undo are owner-only with no superuser exception, like `confirm-all` and the person link: confirming decides what the persona may say. Confirming a rejected item is a 409; `confirm-all` skips rejected items.
- Editing an item sets `confirmed_at` when empty (AC-2.2). Reject and restore never confirm.
- Retrieval filters on `Memory.person_id`, `status != rejected` and `confirmed_at IS NOT NULL` **in the SQL**. The ticket said `... OR was_edited`, but then undo could never stop a corrected item; editing now stamps `confirmed_at` instead, and the migration backfills `confirmed_at` for items already corrected so none is lost (DEV-3).
- `search_persona` ends the caller's read transaction before the model call, like `search_extracted`. Access to the person is checked by the route that calls it (MR-104).

## Risks and how we handle them
- **Two migration heads.** MR-104 also adds a migration; whoever merges second runs `alembic merge heads`.
- **Downgrade is lossy** for confirmations (the column is dropped). No memory text is touched.
- **Backfill reads `was_edited` and `updated_at`**, both existing columns; the migration does not import `app.models`.
- **Flaky e2e from Ollama.** The Playwright spec expects the backend with `AI_BACKEND=fake`.
