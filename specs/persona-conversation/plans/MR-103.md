# Plan: MR-103 Streaming local model client and latency check

ticket: tickets/MR-103.md · spec: NFR-1, NFR-2 · status: draft (plan mode, no code yet)
base: main @ f41ff24

## Goal
Replies can stream from the local model, the fake can stream too (and count calls), and
we know early whether `llama3.1` on the demo machine can show first words within 3 s.

## Files
| File | Change |
|------|--------|
| `backend/app/core/llm.py` | `ChatTurn` dataclass (`role: Literal["user", "assistant"]`, `content: str`); `LLMClient.stream_answer(system: str, turns: Sequence[ChatTurn]) -> Iterator[str]`; `OllamaClient.stream_answer` |
| `backend/app/core/fake_ai.py` | `FakeLLMClient.stream_answer`, `stream_calls`, `stream_chunks`, `error_after` |
| `backend/tests/core/test_llm_stream.py` (new) | Ollama streaming via the existing `fake_langchain` pattern in `test_llm.py` |
| `backend/tests/core/test_fake_ai.py` | fake streaming cases |
| `backend/scripts/measure_persona_latency.py` (new) | p50/p90 time to first chunk and to the end |

## Design
- `OllamaClient.stream_answer`: build `[SystemMessage(system), HumanMessage | AIMessage per turn]`, call `ChatOllama(...).stream(messages)`, yield each non-empty `chunk.content`. Same model, `temperature=0` and timeout as `answer`.
- **Errors inside a generator** are raised while iterating, not when the call is made. Wrap the iteration itself in `_translate_errors()`, so a connection drop mid-reply still becomes a generic `LLMError`.
- Fake: yields `stream_chunks` (default `["Fake ", "answer ", "citing [1]."]`), appends `(system, turns)` to `stream_calls`, raises `LLMError` before the first chunk if `error` is set, or after chunk *n* if `error_after = n` (MR-104 needs this for its mid-stream error test).
- `answer()` stays as it is; `/search/ask` keeps using it.
- Latency script: reads `fixtures/families/thomas.json` and builds a realistic prompt (5 numbered memories, 5 quotes, a 6-turn history), sends 20 questions through `OllamaClient.stream_answer`, and prints p50/p90 first-chunk and total times plus the model name. It refuses to run unless `OLLAMA_BASE_URL` points at `localhost`, `127.0.0.1` or the compose service `ollama` (memorial-privacy rule 1). Synthetic data only; it never touches the database.

## Order
1. `ChatTurn` + protocol method; type-check.
2. Fake + its tests (other tickets can start using it as soon as this merges).
3. Ollama implementation + tests with the LangChain fake (chunks, empty chunks skipped, error before and during the stream).
4. Latency script; run it on the demo machine; post numbers in the ticket.

## Risks and how we handle them
- **First words over 3 s on CPU.** Likely with a ~1.5k-token prompt on an 8B model. The script tells us on day 1, not at the demo. If p90 > 3 s, the tech lead picks a smaller local model or a GPU (spec concern row 9), and the grounding evals run before and after the change.
- **LangChain chunk types.** `chunk.content` can be a list for some models; treat non-str as an error (like `_chat`) rather than guessing.
- **Coverage.** The script lives in `scripts/` and isn't imported by tests, so it doesn't count; keep its logic thin.

## Proof
- AC-N1.1 `test_llm_stream.py::test_stream_answer_fake_and_protocol`, plus `test_stream_error_before_first_chunk`, `test_stream_error_mid_reply_is_generic`
- AC-N2.1 (measurement half): the script's output, posted in `tickets/MR-103.md` Questions

## Rejected
- Raw `ollama.Client(...).chat(stream=True)`: bypasses the LangChain client the rest of `llm.py` uses, so two error paths.
- Streaming through LangGraph `stream_mode="messages"`: needs a LangChain model inside the graph; the fake couldn't take part. MR-105 streams from the client directly.
