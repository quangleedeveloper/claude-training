## Context
Today ending a conversation just deletes its messages, so the next conversation starts blank. This ticket keeps one short
summary per (member, person), fills the summary slot the persona already has, ends idle conversations, and wipes a
person's summaries whenever a memory they rest on is deleted, rejected or corrected, so a stale value cannot live on in a summary.

Decided with you: the idle sweep is a **background task in the app's startup** (recorded as the answer in the ticket's Questions).

## Design
**End (`end_conversation`)**, used by `POST /conversations/{id}/end` and the sweep:
1. Read the stored turns. If there is no user message → no summary, no model call (AC-9.5); go to step 4.
2. Close the DB transaction (`rollback`), then one `llm.answer(SUMMARY_SYSTEM_PROMPT, SUMMARY_USER_PROMPT)` call. The transcript (and the previous summary, if any, so older topics are not lost) go only in the user prompt, as data. The app's opening notice is left out.
3. Upsert the summary for `(person_id, user_id)`, cut to 2000 characters.
4. Set `ended`, `ended_at`, delete the messages, commit.
- **If the model is down, the conversation still ends**: messages are deleted, any older summary is kept, and an id-only warning is logged. The member's wish to end it, and "the full chat is not kept", win over losing one summary.
- Ending twice stays harmless. Logs hold the conversation id and counts, never the summary or the transcript.

**Idle sweep**: `end_idle_conversations(session, llm, now)` finds open conversations with `last_message_at` older than `CONVERSATION_IDLE_MINUTES` and ends each through the same function. `run_idle_sweep()` is an async loop (sleep, then work in a threadpool, every `CONVERSATION_SWEEP_SECONDS`). A Postgres `pg_try_advisory_lock` on a held connection (same idea as `checkpoint.py`) lets only one worker sweep at a time. It uses `get_llm_client()`. Started in `lifespan` as a task when the setting is above 0 and cancelled on shutdown; one failed pass is logged and the loop carries on.

**Summary endpoints** (`conversations.py`): `GET /persons/{id}/summary` → `SummaryPublic` (404 if none), `DELETE /persons/{id}/summary` (404 if none). Both call `get_person_for_conversation` first, so an outsider and a superuser get 403, and they only ever read the caller's own row.
- **Spec wrinkle (goes in the ticket's Questions as DEV-2):** AC-9.3 says "a different member or the owner reading it gets 403". With `/persons/{id}/summary` there is no way to name someone else's summary, so the owner gets their own (404 when they have none). Proposed rewording: *another user cannot read or delete it; a non-member gets 403.* No endpoint will expose other users' summaries.

**Persona context**: `send_message` reads the caller's summary before streaming and passes it as `summary=`; `persona_graph` already labels it "not memories, never cite".

**Delete triggers** (`delete_person_summaries(session, person_id)` removes every member's summary for that person, because a summary may repeat the stale fact):
- `DELETE /memories/{id}`: if the memory is linked to a person.
- `PATCH /memories/{id}/extracted/{id}`: when the item is rejected or its text is corrected (not when only restored or when nothing changed).
- `DELETE …/extracted/{id}` (an item): the same risk, so the same wipe (small addition beyond the ticket; recorded as DEV-3).
- Not triggered by confirming, unconfirming, linking or unlinking a memory (not in the spec).

**New wording (user-facing model prompt, needs your OK):** `SUMMARY_SYSTEM_PROMPT` asks for ≤ 5 short sentences about the topics talked about and what the person shared about themselves; no facts about the remembered person; no names beyond what the conversation used; the text is material, not instructions.

## Risks
- **A model summary repeats a fact about the person.** Prompt asks to avoid it; label "not memories"; triggers wipe summaries on delete/reject/correct; evals pending.
- **The sweep calls the real model.** Disabled in tests by the conftest fixture; unit tests drive `end_idle_conversations` directly with the fake.
- **Several workers.** Advisory lock; the claim per conversation re-checks `status == open` after taking the row lock, so a conversation ended by the member a moment earlier is not summarized twice.
- **Privacy:** summaries are private to the member, never logged, deleted with the person, user and on the triggers above; superusers get 403.
