## Context
Only the owner can talk to a persona today. This ticket lets the owner invite an existing account (an adult, attested by
the owner) to talk with the persona, and revoke them. It changes a privacy rule: a member reaches the persona's replies and
their cited sources, never the memory, file or extracted-memory endpoints. The ticket says the PR needs the Lead and the tech lead.

## Design
- **Invite** `POST /persons/{id}/members` body `{email, adult_confirmed}`. `adult_confirmed` is `Literal[True]` and required, so missing or false is a 422 and nothing is stored (AC-10.2). Look the user up by email; if found, active and not the owner, insert a `PersonMember` unless one exists (idempotent). The response is the same `200 {"message": "If an account exists for that email it can now talk with this persona."}` for a known, unknown, already-invited, inactive or owner's own email (AC-10.3). Nothing about age is stored besides the owner's tick (Q4).
- **List** `GET /persons/{id}/members` (owner): members with email and name (the owner chose them).
- **Revoke** `DELETE /persons/{id}/members/{user_id}` (owner; 404 if not a member). **One transaction**: delete the member row, delete that member's summary for the person, end the member's open conversations for the person **without a summary** and delete their messages, then commit. No model call. Doing it in one commit means a crash cannot leave a revoked member with a live chat that the idle sweep would then summarize.
- **Access**: `get_person_for_conversation` returns the person for the owner or a member, 404 if missing, 403 otherwise. Superusers get no exception. It is the single seam used by open, send and the summary endpoints, so revoked members lose all three at once (AC-10.5: next message 403).
- **Members still get 403 everywhere else**: person, memory, file and extracted-memory routes already check ownership; tests pin it (AC-10.4, AC-2.5).
- **Cited sources**: a member sees `done.sources` as today (item content and memory title, plus ids). Memory and file ids in them are not usable (all those endpoints 403), so I leave the shape alone; flagged below.

## Risks and open points (go in the ticket's Questions)
1. **A member cannot find the persons they belong to.** `GET /persons/` lists only the caller's own, and `GET /persons/{id}` is owner-only, so a member has no way to learn a person id or name. The API for it (e.g. `GET /persons/shared`) is not in this ticket or the spec; I will not add it and will raise it as a question for the BA, since the UI will need it.
2. **Account enumeration by timing or by `GET members`**: the invite response is identical, but timing is not equalised (same as the existing login code needs a dummy hash). Accepted for v1, noted.
3. **Sources shown to members** include ids as well as text; harmless today, to be revisited if member-facing UI wants a slimmer shape.
4. **Privacy rule change** (rule 2): reviewers must include the Lead and the tech lead.
