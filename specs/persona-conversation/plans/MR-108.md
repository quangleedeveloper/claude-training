## Context
A member (or the owner) can talk with the persona but cannot add to it; only the owner adds memories. FR-11 lets a member
*offer* a memory as text; the owner decides. Nothing said in a chat becomes a memory any other way (AC-11.4), so accepting is the
single door from a conversation into the family's memories, and a human opens it.

## Design
- `POST /persons/{id}/offers` body `{content}`: owner or member (`get_person_for_conversation`; outsiders and superusers 403, unknown person 404). Stores a row and answers `{"message": "Your offer was sent to the family."}`. Nothing else changes (AC-11.1): no `Memory`, no extraction. At most **20 waiting offers per member per person** (409 "Too many offers are waiting for the family to review"), so one member cannot flood the owner's list; the limit is mine, not in the spec (DEV note).
- `GET /persons/{id}/offers` (owner only, `get_person_or_error`): newest first, with the offerer's name or email so the owner knows who sent it.
- `POST /persons/{id}/offers/{offer_id}/accept` (owner only): in **one transaction** lock the offer row (`FOR UPDATE`, so a double click cannot make two memories), create a `Memory` owned by the owner, linked to the person (`person_id`), `person_name` = the person's name, `content` = the offer text, `title` = "Offered: " + the first 60 characters of the text (the memory model needs a title; the owner can rename it), delete the offer, commit; then queue `extract_memory_story` as the normal create route does. Items start unconfirmed (extraction never confirms), so the persona cannot use them until the owner confirms (AC-11.2). Returns the `MemoryPublic`.
- `DELETE /persons/{id}/offers/{offer_id}` (owner only): deletes the offer (AC-11.3). Unknown or another person's offer: 404.
- Everything about an offer is checked against the path's person (an offer id from another person is a 404, never an access leak).
- Logs hold ids only, never the offer text.
- A revoked member's waiting offers stay until the owner decides (the spec does not say to drop them; deleting a user or a person cascades them).

## Open points (go in the ticket's Questions)
1. Memory **title** for an accepted offer is generated ("Offered: …"); proposed, the BA may prefer another.
2. The **20-offer cap** per member and person is mine.
3. An accepted offer is deleted (it became the memory), so the owner cannot later see who sent it; if that matters, store `offered_by` on the memory (new column, not in this ticket).
4. Waiting offers of a **revoked member** stay for the owner to decide.

## Outcome (2026-10-29)
- Built as planned: `memoryoffer` table, `POST` and `GET /persons/{id}/offers`, `POST …/offers/{offer_id}/accept` and `DELETE …/offers/{offer_id}`, with the 20-waiting-offers cap per member and person.
