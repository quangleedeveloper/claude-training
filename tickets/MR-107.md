## What to build
- `personmember` table and migration; `adult_confirmed` required true.
- `POST /persons/{id}/members` (by email, generic response either way), `GET`, `DELETE /persons/{id}/members/{user_id}`. Owner only.
- Widen `get_person_for_conversation` to members. Members get persona replies and their cited sources only; every memory, file and extracted-memory endpoint still returns 403 for them.
- Revoke: end the member's open conversations **without** a summary, delete their summary, next message 403.
- Update the `memorial-privacy` skill (rule 2) in the same PR: members of a person see that persona's replies and cited sources, nothing else.

### Dev → BA · 2026-10-29
**DEV-1. A member cannot find the persons they belong to.** `GET /persons/` lists only the caller's own persons and `GET /persons/{id}` is owner-only, so an invited member has no way to learn a person id or name. The spec has no endpoint for it. Proposed: `GET /persons/shared` returning `{id, name}` for the persons the caller is a member of (no owner data, no memories). Not built here; the UI for members will need it. OK to add as a ticket?
**DEV-2. Files outside the list.** `app/api/routes/conversations.py` (access to the person is now checked before the "ended" check, so a revoked member gets 403 rather than 409), `app/services/conversation_summary.py` (`end_member_conversations`, used by revoke), `tests/utils/person.py` (`add_member`), and the regenerated frontend client.
**DEV-3. Invite answer.** The same 200 and message for a known, unknown, already-invited, inactive or owner's own email (AC-10.3). Response time is not equalised, so timing could still tell them apart. Bigger: `GET /persons/{id}/members` shows whether an invite became a member, so any account that can create a person can test whether an email has an active account (found by the automated security review). Closing it means pending invites the invitee accepts, which changes AC-10.1/10.3; not built. Needs a decision from the Lead (or rate limiting on invites).
**DEV-4. Sources shown to members** are the same objects the owner gets (item text, memory title, and ids). The ids lead nowhere because every memory, file and extracted-item endpoint returns 403 for members. If the member UI wants a slimmer shape, that is a follow-up.
**DEV-5. Review.** This changes `memorial-privacy` rule 2, so the PR needs the Lead and the tech lead (ticket notes).
**DEV-6. Races closed in this PR** (security review and verifier): `send_message` locks the conversation row before checking access and status; the stream stops if the conversation ended meanwhile; revoke ends conversations first, then deletes every message of the pair; `end_conversation` writes no summary for someone who is no longer owner or member. Left: a reply already streaming when a member is revoked still finishes for them (nothing is stored).
