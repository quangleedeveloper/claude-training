## What to build
- `GET /memories/` accepts an optional `person_id` and returns only the caller's memories linked to that person (a superuser keeps today's wider view). No `person_id` behaves exactly as before.
- A "Memories" item in the People actions menu opens a dialog listing the titles of the memories linked to that person, with a count, an empty state, and a link to the Memories page.

## Files
`backend/app/api/routes/memories.py`, `backend/tests/api/routes/test_memories.py`, regenerated `frontend/src/client/`, `frontend/src/components/Persons/PersonMemories.tsx` (new), `PersonActionsMenu.tsx` (one item), `frontend/tests/person-memories.spec.ts`. No migration.

## Notes
- Titles only in the dialog; the stories stay on the Memories page.
- Filtering is in SQL, on top of the existing owner scoping, so another user's person id returns an empty list, not their data.

## Done when
- Backend tests: filter returns only the linked memory; another user's person id gives an empty list; a bad id is a 422
- Playwright: linked memories listed and others left out, empty state, the request carries `person_id`
- Reviewed and approved by a code owner
